# Virtual Thread

虛擬執行緒（Virtual Thread）是 Java 21 提供的輕量級執行緒模型。它保留了傳統「一個任務一個執行緒」的直觀程式設計方式，同時把大量排程成本從作業系統搬到 JVM 層，因此特別適合高併發、阻塞型、IO 密集型業務。

對於微語客服系統這類同時連接使用者、坐席、第三方渠道、AI 服務、呼叫系統、知識庫抓取任務的應用來說，大量請求並不是一直在消耗 CPU，而是在等待網路、資料庫、Redis、WebSocket、IMAP 與第三方介面返回。虛擬執行緒的價值，正是在這些「等待很多、併發很高」的場景中體現出來。

## 微語客服系統中的使用方式

目前專案已經在多個模組中實際使用虛擬執行緒，並不是只停留在設定層面。

### 1. 作為 Spring 非同步任務的預設執行模型

系統啟動設定中已經開啟：

```properties
spring.threads.virtual.enabled=true
```

同時，核心模組中定義了統一的非同步執行器，將 Spring 的 `@Async`、`applicationTaskExecutor` 等入口適配到虛擬執行緒執行器上。這樣一來，下列場景都可以延續 Spring 既有程式設計模型：

- 事件監聽器
- 非同步通知
- 後台匯入任務
- 非關鍵鏈路的業務回呼

而不需要把整個程式碼庫全面改寫成反應式風格。

### 2. 用在客服系統裡典型的阻塞型 IO 場景

專案裡已經有多類真實業務直接使用 `Executors.newVirtualThreadPerTaskExecutor()` 或 `Thread.startVirtualThread()`，包括：

- 知識庫整站抓取：抓取服務會並發訪問大量頁面，任務大部分時間消耗在 HTTP 請求與頁面抓取等待上。
- 呼叫中心與 FreeSWITCH ESL：回呼處理、背景任務與連線相關流程都包含大量網路等待。
- 企業微信、飛書等渠道整合：收到回呼後，系統會非同步同步訊息或啟動長連線，避免阻塞 Web 請求執行緒與系統初始化流程。
- AI 串流輸出：例如 SSE 場景下，一個虛擬執行緒可以承載一次串流生成流程，同時保留順序式可讀程式碼。
- 郵件 IDLE 監聽、Janus/WebRTC 用戶端：這類長連線、等待導向的任務非常適合交給虛擬執行緒處理。
- Redis 過期事件後的補償處理：例如超時補償邏輯可以快速啟動虛擬執行緒執行，而不阻塞事件分發路徑。

### 3. 在需要「順序語義」的地方配合使用

專案並不是把所有地方都改成「無限制併發」。例如呼叫模組中的部分回呼執行器仍保留單執行緒語義，只是把底層執行緒工廠切換為虛擬執行緒。這樣既能維持事件順序，也能降低執行緒資源成本。

這也是目前專案使用虛擬執行緒的原則：

- 需要高併發等待時，使用每任務一個虛擬執行緒。
- 需要順序消費時，保留順序模型，但讓執行緒更輕。
- 需要明確限流、排隊或背壓時，繼續使用傳統執行緒池。

## 為什麼微語客服系統適合虛擬執行緒

微語客服系統的業務特性，決定了它天然適合虛擬執行緒。

### 1. 系統裡有大量等待型任務

客服系統看起來業務複雜，但很多鏈路的核心特徵並不是高 CPU 計算，而是大量等待：

- 等待使用者訊息
- 等待第三方渠道回呼
- 等待 AI 回覆
- 等待 FreeSWITCH、Janus 或 WebSocket 事件
- 等待 Redis、資料庫或郵件伺服器回應

如果這些任務全部壓在平台執行緒上，系統就容易出現執行緒膨脹、排隊堆積與上下文切換開銷變大的問題。虛擬執行緒更適合承接這類高併發等待。

### 2. 客服業務經常出現突發併發

行銷活動、渠道投放、機器人大量接入、工單匯入、知識庫抓取、呼叫事件風暴，都可能造成瞬時任務數上升。傳統執行緒池通常需要提前預估核心執行緒數、最大執行緒數與佇列大小，但實際峰值很難精準預測。

虛擬執行緒無法取代容量規劃，但可以明顯降低「執行緒資源先成為瓶頸」的機率，讓系統更從容地承接尖峰流量。

### 3. 可以保留現有 Spring MVC / JPA 程式設計模型

微語客服系統是一個典型的 Spring Boot 多模組應用，已經存在大量同步式服務、事件監聽器、JPA 存取模式與第三方 SDK 整合。

如果為了提升併發能力而全面改造成反應式架構，成本很高，風險也大。虛擬執行緒提供了一條更務實的路徑：

- 保留既有程式碼結構
- 保留目前的服務層與交易模型
- 保留大部分同步 API 寫法
- 在 Java 21 上獲得更好的併發承載能力

對一個持續演進的客服平台來說，這是投入產出比很高的技術升級方式。

## 使用虛擬執行緒帶來的好處

### 1. 提升高併發 IO 場景下的吞吐能力

當系統同時處理大量外部呼叫、長時間等待與非同步事件時，虛擬執行緒可以讓更多任務處於掛起狀態，而不必為每個等待中的任務佔用昂貴的平台執行緒。

### 2. 降低執行緒池調參複雜度

傳統執行器常常需要在核心執行緒數、最大執行緒數與佇列大小之間取捨。參數設得太小容易堆積，設得太大又可能帶來執行緒切換與記憶體壓力。虛擬執行緒無法消除所有調優工作，但能明顯降低執行緒數量配置的壓力。

### 3. 讓程式碼維持直觀與可維護

相較於大量回呼或大規模反應式改造，虛擬執行緒允許專案繼續使用順序式業務程式碼。對於客服流程這種分支很多、例外處理複雜的場景，這點對長期維護非常重要。

### 4. 更適合長連線與外部系統整合

客服平台天然會接入很多外部系統：企業微信、飛書、郵件、AI、語音閘道與 WebRTC 閘道等。只要這些鏈路主要以阻塞等待為主，虛擬執行緒通常都比單純擴大平台執行緒池更合適。

## 壓測與效能收益建議

虛擬執行緒是否帶來明顯收益，最終還是要用壓測資料驗證。對微語客服系統來說，建議不要只做單一介面的微基準測試，而要圍繞真實業務鏈路做對比。

### 1. 建議優先壓測的場景

- 客服訊息接入鏈路：模擬訪客訊息、渠道訊息與機器人訊息同時進入系統。
- AI 串流回覆鏈路：重點觀察 SSE 長連線數量增加時的穩定性。
- 呼叫中心事件鏈路：模擬 FreeSWITCH / ESL 事件高頻進入時的處理能力。
- 知識庫整站抓取：對比多頁面抓取時的吞吐量與資源使用。
- 郵件監聽與第三方回呼：觀察大量等待型任務同時存在時的執行緒與記憶體表現。

### 2. 建議的對比方式

至少保留兩組測試：

- 一組使用傳統執行緒池設定。
- 一組啟用目前的虛擬執行緒設定。

對比時儘量保持其他變數一致，例如：

- 相同 JDK 版本
- 相同資料庫與 Redis 設定
- 相同外部依賴延遲
- 相同 JVM 堆大小與機器規格

這樣才能讓差異更多聚焦在執行緒模型本身，而不是環境噪音。

### 3. 建議重點觀察的指標

不要只看 QPS，建議至少一起觀察：

- 平均延遲
- P95 / P99 延遲
- 併發連線數或併發任務數
- JVM 執行緒數量
- CPU 使用率
- 堆內存與非堆內存變化
- Full GC / Young GC 次數
- 超時率與錯誤率

對客服系統來說，很多時候真正重要的不是峰值吞吐，而是在高併發等待場景下，系統是否仍然穩定、尾延遲是否惡化、錯誤率是否升高。

### 4. 在微語客服系統中，預期可以看到哪些收益

如果壓測場景以阻塞等待為主，通常可以重點關注這些變化：

- 在相同機器規格下承載更多併發等待任務。
- 在長連線、回呼與外部介面等待同時存在時，執行緒資源更不容易先耗盡。
- 高併發場景下，因執行緒池排隊導致的尾延遲惡化有所緩解。
- 某些原本需要複雜執行緒池調參的業務，設定成本會下降。

需要強調的是，這裡的「收益」更常體現在系統承載力與穩定性改善，而不一定是所有場景下 CPU 使用率或單請求耗時都直接大幅下降。

### 5. 應如何解讀壓測結果

如果測試結果顯示收益明顯，通常表示該鏈路確實是典型的 IO 密集型、等待型業務，適合繼續使用虛擬執行緒。

如果收益不明顯，常見原因包括：

- 該場景本身更偏 CPU 密集型
- 真正瓶頸在資料庫、Redis 或第三方依賴
- 下游容量太小，執行緒模型不是主要矛盾
- 業務中仍然存在顯式串行點或鎖競爭

因此，虛擬執行緒壓測的目標不應是「證明它在所有場景都更快」，而是識別哪些鏈路最適合它，哪些鏈路仍然需要傳統背壓、快取、批次、佇列或其他架構優化。

## 為什麼我們不是所有地方都改成虛擬執行緒

虛擬執行緒很適合目前系統，但它不是萬能解法。

### 1. CPU 密集型任務收益有限

如果任務本身主要消耗 CPU，例如重度計算、編解碼或長時間佔用核心的演算法處理，那麼虛擬執行緒不會憑空創造更多算力。

### 2. 需要明確背壓的場景仍應保留執行緒池

專案裡仍保留一些傳統執行緒池設定，用在需要限制併發度、保護下游系統或明確拒絕策略的場景。這裡關注的核心不是「執行緒是否足夠輕」，而是「系統邊界是否足夠穩定」。

### 3. 非同步之後仍要注意上下文傳遞

專案中的部分切面已經明確說明：如果程式碼仍依賴 `HttpServletRequest` 等請求上下文，就不能直接把整段邏輯丟進非同步執行。這不是虛擬執行緒獨有的問題，而是所有非同步模型都必須注意的上下文邊界。

## 小結

在微語客服系統中，虛擬執行緒並不是為了追逐新特性而啟用，而是因為它和系統的實際運作特徵高度匹配：

- 系統存在大量高併發、阻塞型、等待型任務。
- 系統整合了大量外部渠道與長連線能力。
- 系統希望在不推翻現有 Spring 架構的前提下提升併發承載能力。

因此，專案選擇在 Java 21 基礎上引入虛擬執行緒，並將其落地到 Spring 非同步執行器、網站抓取、呼叫中心整合、AI 串流輸出、渠道回呼、郵件監聽與 WebRTC 閘道用戶端等真實場景中。

對於客服系統這類典型的 IO 密集型平台來說，虛擬執行緒是一種非常務實的技術升級：它不要求徹底重寫架構，卻能明顯改善系統在高併發等待場景下的可擴展性與可維護性。
