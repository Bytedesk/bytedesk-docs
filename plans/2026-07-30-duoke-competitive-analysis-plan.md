## 一、多客核心能力提炼

### 1.1 自进化 AI 客服（核心差异化）

| 能力 | 描述 |
| ------ | ------ |
| **自主处理售后** | AI 自动查订单、核对售后条件、收集凭证、按规则给出退款/补发方案 |
| **无人值守服务** | 深夜无人值班时，售后也能正常推进，无需人工反复确认 |
| **持续自进化** | 从真实会话中学习优秀应答，自动提炼有效判断逻辑与处理流程，沉淀为 Skill |
| **知识库自动补充** | 每天从真实会话中学习优秀应答，持续补充店铺知识库 |

### 1.2 多 Agent 架构 + 多 Skill 体系

| 组件 | 描述 |
| ------ | ------ |
| **客服 Agent** | 承接客户服务，处理买家问题 |
| **店铺参谋 Agent** | 帮助卖家发现经营机会，分析数据、预警风险 |
| **Skill 商店** | 内置丰富现成 Skill，一键启用覆盖常见业务场景 |
| **智能提取 Skill** | 上传产品资料、客服 SOP、店铺规则 → 自动生成专属 Skill |
| **自进化 Skill** | 基于会话及店铺知识自动沉淀优质 Skill，根据优秀人工客服经验迭代优化 |

### 1.3 AI 员工能力矩阵

| 能力 | 描述 |
| ------ | ------ |
| **多语言** | 130+ 语种实时互译，面向不同国家买家 |
| **意图理解** | 结合对话上下文理解买家真实意图 |
| **场景适配** | 根据不同场景灵活调整沟通方式 |
| **品牌语气** | 卖家可自定义品牌语气，延续店铺服务风格 |
| **自主执行** | 不只是聊天，能查询数据、调用 Skill、真正处理完问题 |
| **旺季承载** | 高峰 80%+ 日常客服工作由 AI 承载 |

### 1.4 店铺参谋（经营分析 Agent）

| 能力 | 描述 |
| ------ | ------ |
| **自然语言问数** | 像聊天一样提问，自动汇总分析订单、营收、转化、售后、评价 |
| **异常发现** | 快速发现数据异常并定位原因 |
| **优化建议** | 给出具体优化建议，过去几小时的工作缩短到 1 分钟 |

### 1.5 多渠道与电商平台整合

| 能力 | 描述 |
| ------ | ------ |
| **平台接入** | Shopee、TikTok Shop、Mercado Libre、Lazada 等主流电商平台 |
| **统一管理** | 多店铺消息统一管理 |
| **7×24 接待** | 全球 7×24 小时在线 |
| **附加工具** | 智能跟单、消息群发、差评预警、评价管理 |

## 二、微语现状对比

| 多客能力 | 微语现状 | 差距 |
| ---------- | ---------- | ------ |
| 自进化 AI（自动沉淀 Skill） | TODO 中有"自进化"规划项，但尚未实现 | **较大** |
| Skill 商店 | 有 skills 概念（`modules/ai` 中），但无商店/市场机制 | **大** |
| 智能提取 Skill | 无 | **缺失** |
| 店铺参谋（经营分析 Agent） | 有 BI 模块，但无对话式分析 Agent | **大** |
| 自动售后处理（退款/补发） | 工单模块有自动化能力，但未深度对接订单系统 | **中等** |
| 多语言翻译 | 有 i18n 体系，但无实时翻译 | **中等** |

### 2.1 仓库内已存在的可复用锚点

当前规划不需要从 0 开始。仓库里已经有一批可以直接复用的基础能力，后续实现时应优先基于这些入口扩展，而不是重新造一套平行体系。

| 能力方向 | 当前入口 | 可复用方式 |
| ---------- | ---------- | ------------ |
| Skill 基础实体 | `modules/ai/src/main/java/com/bytedesk/ai/skill/SkillEntity.java`、`SkillRestService.java` | 已有 Skill 的 CRUD、初始化和 classpath 扫描能力，可作为 Skill 商店与 Skill 版本化的基础 |
| Skill 后台入口 | `frontend/apps/admin/src/pages/Dashboard/Super/Robot/skill/SkillTable.tsx`、`frontend/apps/admin/src/apis/ai/skill.ts` | 已有平台技能列表，但当前偏只读展示，缺少创建/编辑/绑定/版本/审核等运营能力 |
| 主 AI 运行时 | `modules/ai/src/main/java/com/bytedesk/ai/service/BaseSpringAIService.java` | 是机器人问答主链路的稳定入口，适合插入“Guidance / Skill 匹配 / 自进化观察”能力 |
| Prompt 组装 | `modules/ai/src/main/java/com/bytedesk/ai/service/PromptHelper.java` | 当前仍以 prompt + 历史消息 + KB 上下文为主，后续可扩展为分段式上下文组装 |
| 知识库检索 | `modules/ai/src/main/java/com/bytedesk/ai/service/KnowledgeBaseSearchHelper.java` | 已具备 FAQ / Text / Chunk / Webpage 聚合检索，可作为自进化知识补充的输入来源 |
| Tool 注册与调用 | `modules/ai/src/main/java/com/bytedesk/ai/tool/ToolTools.java` | 已有 Tool 基础设施，可承接 AI 自主办事能力的工具层 |
| Tool 审批 | `modules/ai/src/main/java/com/bytedesk/ai/tool_approval/*` | 可直接复用于高风险动作的审批门槛设计 |
| Tool 审计 | `modules/ai/src/main/java/com/bytedesk/ai/tool_audit/*` | 可作为 AI 自主执行、规则自动动作的审计闭环 |
| Memory 能力 | `enterprise/ai/src/main/java/com/bytedesk/ai/memory/MemoryTools.java`、`enterprise/ai/src/main/java/com/bytedesk/ai/alibaba/memory/*` | 可作为用户长期记忆、经验沉淀、对话事实复用的存储入口 |
| 订单工具 | `enterprise/core/src/main/java/com/bytedesk/core/open_order/OrderTools.java` | 说明微语已经有订单工具入口，后续只需补强“可安全执行的业务动作” |
| 电商渠道基础 | `channels/shop/`、`modules/shop/`、`frontend/apps/admin/src/pages/Dashboard/Open/Shop/ShopTable.tsx` | 已有 shop 模块与后台管理入口，可作为电商连接器能力的扩展基础 |
| 会话关闭后自动化 | `enterprise/ticket/src/main/java/com/bytedesk/ticket/ticket_settings_auto_create/TicketAutoCreateService.java`、`docs/plans/2026-07-28-auto-summary-quality-check-plan.md` | 已经在做自动建单/总结/质检，适合作为“自进化观察链路”的第一批数据来源 |

### 2.2 当前结构性短板

虽然已有不少基础能力，但当前与多客相比，缺口不是“没有 AI”，而是“缺少把 AI 运营起来的中间层”。

1. Skill 已经存在实体，但当前更接近“技能条目/描述信息”，不是可运行、可版本化、可评估的执行资产。
2. `SkillRequest` 当前没有暴露 `type` 字段，前端虽按 `type` 查询但类型定义也未包含，说明 Skill 的业务分类链路尚未完整打通。
3. `SkillTypeEnum` 当前是 `GENERAL / WORKFLOW / DEVELOPMENT / REVIEW / TESTING / DOCUMENT / DESIGN / MEDIA / DATA`，偏通用开发技能分类，缺少售前、售后、工单、订单、质检、呼叫中心等客服运营分类。
4. 主问答链路仍以 prompt 拼装为主，缺少每轮动态选择规则、工具、品牌语气、风险策略的控制层。
5. Tool、Order、Memory 已具备基础接口，但尚未形成“可配置授权 -> 可控执行 -> 可审计回放”的客服闭环。
6. 自动总结、自动质检、自动建单等能力已在规划或局部实现中，但缺少统一的数据回流机制，无法进一步沉淀为 Skill 或知识条目。
7. 电商、CRM、工单、订单、知识库、统计等模块都在，但还没有一个统一的 Agent 编排视角把它们组织起来。

## 三、值得微语借鉴的核心方向

### 3.1 自进化能力体系（优先级：⭐⭐⭐⭐⭐）

多客最核心的差异化是"自进化"——AI 在真实服务中自动学习、沉淀经验。

**建议微语实现：**

1. **会话自动评分与筛选**
   - 对每次 AI 对话进行自动质量评分（解决率、用户满意度、人工复核）
   - 高分会话自动提取为优质应答模板
   - 低分会话标记为待人工优化

2. **Skill 自动沉淀**
   - 从人工客服的优秀处理案例中自动提取处理逻辑
   - 将常见问题的解决路径自动转化为 Skill
   - 支持人工审核后发布为正式 Skill

3. **知识库自动补充**
   - 从对话中发现知识库未覆盖的问题
   - 自动生成 FAQ 草稿，人工确认后入库
   - 标记过时/矛盾的知识条目

> 微语 TODO 中已有相关项："自进化功能。自动评价提取聊天记录，将评分高的自动收录知识库"、"AI客服机器人通过自我模拟客户对话，AI评分，AI补充完善知识库，实现agent自我进化"

### 3.2 Skill 体系建设（优先级：⭐⭐⭐⭐⭐）

多客的 Skill 体系非常成熟，微语可重点借鉴：

1. **Skill 商店/市场**
   - 内置常用客服场景 Skill 模板（售前咨询、售后处理、投诉安抚、物流查询等）
   - 支持一键启用
   - 支持社区共享/租户间分享

2. **智能提取 Skill**
   - 上传 SOP 文档 → 自动生成 Skill
   - 上传产品手册 → 自动生成产品知识 Skill
   - 上传客服话术 → 自动生成应答 Skill

3. **Skill 编排与组合**
   - 多个 Skill 可组合为更复杂的工作流
   - 支持条件分支、优先级设置
   - 可视化 Skill 编排画布

### 3.3 经营分析 Agent（优先级：⭐⭐⭐⭐）

多客的"店铺参谋"让非技术人员通过自然语言查询经营数据，这对微语的 BI 模块很有参考价值。

**建议微语实现：**

1. **对话式数据分析**
   - 在管理后台嵌入数据分析对话窗口
   - 支持自然语言查询："今天的会话量是多少？"、"哪个客服满意度最高？"
   - 自动生成图表和洞察

2. **异常预警**
   - 自动监控关键指标（会话量突增/骤降、满意度异常、排队时长飙升）
   - 通过企业微信/邮件/站内通知推送预警

3. **优化建议**
   - AI 根据数据趋势给出优化建议
   - 如："近期转人工率上升15%，建议检查机器人知识库覆盖情况"

> 微语 TODO 中已有相关项："微语助手-在管理后台嵌入漂浮框可以通过问答直接查询当前租户下所有数据"

### 3.4 AI 自主业务处理（优先级：⭐⭐⭐⭐）

多客 AI 不只是回答问题，还能真正"办事"——查订单、退款、补发。

**建议微语实现：**

1. **订单深度集成**
   - 完善 `OrderEntity` 相关 Tools
   - AI 可查询订单状态、物流信息、修改订单
   - 支持退款/退货/补发等操作（需人工确认或规则自动执行）

2. **工单自动闭环**
   - 常见问题 AI 直接处理并关闭工单
   - 复杂问题自动升级人工，并附带 AI 预处理摘要
   - 处理结果自动同步到 CRM/订单系统

3. **自动化规则引擎**
   - "if 订单状态=已签收 且 时间<7天 且 用户诉求=退货 → 自动发送退货地址"
   - 支持可视化配置自动化规则

> 微语 TODO 中已有相关项："AI大模型对话过程中支持查询订单OrderEntity"、"AI客服代理（AI Customer Agents），能接电话、回邮件、处理退款、安抚客户"

### 3.5 多渠道实时翻译（优先级：⭐⭐⭐）

多客支持 130+ 语种实时互译，这对微语的国际化有帮助。

**建议微语实现：**

1. **消息实时翻译**
   - 访客发送外语消息 → 自动翻译为客服语言
   - 客服回复 → 自动翻译为访客语言
   - 翻译结果与原文同时展示

2. **知识库多语言**
   - 知识库内容自动翻译为多语言版本
   - 根据访客语言自动匹配对应知识库

### 3.6 电商平台深度对接（优先级：⭐⭐⭐）

多客已接入 Shopee、TikTok Shop、Mercado Libre、Lazada 等主流电商平台。

**建议微语实现：**

1. **电商平台连接器**
   - 完善 `channels/shop` 模块
   - 支持主流电商平台消息接入
   - 统一多店铺/多平台消息管理

2. **差评预警与评价管理**
   - 自动监控电商平台差评
   - 差评出现时自动通知 + 创建工单跟进
   - 评价统一管理面板

### 3.7 不建议直接照搬的部分

多客的宣传重点明显偏全球电商卖家场景，微语则是更广义的客服平台、工单平台、在线客服、呼叫中心与 Agent 能力平台。因此规划时需要“借鉴能力模型”，而不是照抄产品形态。

1. 不建议把“店铺”作为唯一核心抽象，微语应继续以组织、工作组、机器人、渠道、工单、订单为基础模型。
2. 不建议第一阶段就围绕 Shopee/TikTok Shop 做大量定制 UI，应优先抽象出通用“外部业务连接器 + 外部对象工具”模型。
3. 不建议直接承诺“80%+ 日常客服工作由 AI 承载”这类结果指标，微语当前更需要先补观测、审计、审批和可回滚能力。
4. 不建议先做纯营销导向的 Skill 商店，应该先做内部可运营的 Skill 模板库，再考虑开放市场化分发。

## 四、规划边界与设计原则

### 4.1 本规划的目标

本规划的目标不是马上重做整套 AI 架构，而是为微语补出一个位于现有模块之上的“Agent 运营层”。该层负责：

1. 把当前分散在 prompt、知识库、规则和人工经验中的能力沉淀为 Skill 资产。
2. 把对话、工具执行、订单动作、工单结果、人工接管等过程记录成可回放、可分析的数据。
3. 把自动总结、自动质检、自动建单、自进化知识补充等现有能力打通成闭环。
4. 在不破坏现有客服主链路的前提下，逐步提高 AI 自主办事能力。

### 4.2 本规划的非目标

1. 不在第一阶段重写 `BaseSpringAIService` 主运行时。
2. 不在第一阶段直接引入不可控的自动执行能力，如无审批自动退款、自动修改外部业务系统核心数据。
3. 不在第一阶段新建一套与现有 `SkillEntity`、Tool、Memory 并行的重复系统。
4. 不在第一阶段强绑定某一家电商平台的私有流程。

### 4.3 设计原则

1. **最小侵入**：优先复用现有 `modules/ai`、`enterprise/ai`、`modules/shop`、`enterprise/ticket` 能力。
2. **运营优先**：先补资产化、审批、审计、回放、评估，再逐步增加自动执行。
3. **分层落地**：先做内部模板与规则，再做自动提取与自进化，再做外部开放能力。
4. **多租户隔离**：Skill、记忆、工具权限、审计、知识沉淀都必须按 org 隔离。
5. **人工兜底**：高风险业务动作必须支持人工确认、审批和显式回滚。

## 五、建议落地架构

### 5.1 建议新增的中间层

建议在当前机器人问答与业务工具之间新增 4 个中间能力层：

| 层级 | 作用 | 建议落点 |
| ------ | ------ | ---------- |
| Skill Registry | 管理 Skill 模板、分类、绑定关系、版本状态 | `modules/ai` |
| Agent Guidance Layer | 决定本轮启用哪些 Skill、上下文、品牌语气、工具策略 | `modules/ai` |
| Agent Observation Layer | 记录对话、工具动作、人工接管、评分、质检结果 | `modules/ai` + `enterprise/ai` |
| Agent Ops Console | 后台运营界面，用于查看、审核、发布、回放、分析 | `frontend/apps/admin` |

### 5.2 建议复用的现有业务域

| 业务域 | 当前模块 | 后续定位 |
| ------ | ---------- | ---------- |
| 在线问答 | `modules/ai` | 保持主问答入口 |
| 工具执行 | `modules/ai/tool*` | 承接 AI 调用工具、审批、审计 |
| 长期记忆 | `enterprise/ai/memory` | 承接用户画像、事实记忆、经验记忆 |
| 订单能力 | `enterprise/core/open_order` | 承接订单查询、物流、售后动作 |
| 工单自动化 | `enterprise/ticket` | 承接 AI 办事后的闭环输出 |
| 电商连接器 | `channels/shop`、`modules/shop` | 承接外部平台消息/订单/评价同步 |
| 统计分析 | `enterprise/service`、`enterprise/ticket`、`enterprise/call` | 作为经营分析 Agent 的数据基础 |

### 5.3 建议补充的数据资产

在不推翻现有结构的前提下，建议未来按需新增以下数据资产：

1. `SkillTemplate` 或扩展现有 `SkillEntity`，增加模板分类、状态、适用场景、风险等级。
2. `SkillVersion`，用于草稿、发布、回滚、差异对比。
3. `SkillBinding`，用于绑定 robot、workgroup、agent assistant、channel、shop。
4. `AgentObservation`，用于记录本轮命中哪些 skill、是否触发 tool、是否转人工、是否未解决。
5. `SkillOptimizationDraft`，用于保存 AI 生成的优化草案和人工审核结论。

### 5.4 推荐的第一阶段建模决策

建议第一阶段采用“保留现有 `SkillEntity` + 新增版本/绑定实体”的兼容演进方案，而不是把所有字段都塞进现有 `SkillEntity`。

原因如下：

1. 现有 `SkillEntity` 已用于内部 classpath Skill 初始化和平台技能列表，直接大幅改造容易影响已有能力。
2. Skill 商店需要版本、草稿、发布、回滚、审核，这些不适合全部放在主表。
3. Skill 绑定会面向 robot、workgroup、assistant、channel、shop 等多种对象，是典型多对多关系，应单独建模。
4. 后续自进化生成的是“优化草稿”，需要先关联到某个版本和诊断报告，再由人工审核发布。

第一阶段建议：

| 对象 | 建议 | 说明 |
| ------ | ------ | ------ |
| `SkillEntity` | 小幅扩展 | 增加客服运营分类、状态、风险等级、是否模板等元数据 |
| `SkillVersionEntity` | 新增 | 保存 instruction、references、toolPolicy、processPolicy、evaluationPolicy、发布状态和 changelog |
| `SkillBindingEntity` | 新增 | 绑定 robot / workgroup / assistant / channel / shop，支持启停和优先级 |
| `SkillOptimizationDraftEntity` | 第二阶段新增 | 自进化生成草稿时再落地，第一阶段只预留关系 |
| `AgentObservationEntity` | 第二阶段新增 | 观察链路建立时再落地，第一阶段先定义字段草案 |

### 5.5 第一阶段 API 与前端入口建议

后续实现时建议优先补齐以下接口和页面能力：

| 层级 | 建议补齐 |
| ------ | ------ |
| 后端 API | Skill 创建/编辑、SkillVersion 草稿保存/发布/回滚、SkillBinding 绑定/解绑/启停 |
| 前端类型 | `SKILL.SkillRequest` 补齐 `type`、`status`、`riskLevel`、`template` 等字段 |
| 后台页面 | 在现有平台技能列表基础上增加 Drawer，用于编辑基础信息、版本、绑定对象 |
| 绑定入口 | RobotSettings / WorkgroupSettings / AgentSettings 中增加“启用 Skill”配置入口 |
| 审核入口 | SkillVersion 发布前展示 diff、变更说明、影响范围 |

## 七、实施依赖与风险

### 7.1 关键依赖

1. `modules/ai` 已按 5.4 推荐采用“保留现有 `SkillEntity` + 新增 `SkillVersionEntity`/`SkillBindingEntity`”方案，实施时不允许推翻此决策另建平行体系。
2. `enterprise/ai` 的 Memory、自动总结、自动质检能力需要统一事件或数据出口，避免各自孤立。
3. 订单、物流、退款等业务动作依赖外部系统接口时，必须先定义权限边界与幂等策略。
4. 统计分析 Agent 依赖指标定义收口，否则自然语言问数会因口径不一致导致误导。

### 7.2 主要风险

1. 如果直接在第一阶段追求“自动办事”，会绕过审批和审计，风险过高。
2. 如果先做花哨的 Skill 商店 UI，而不先解决版本、绑定、回放、审核，后续会返工。
3. 如果自进化直接写回线上 Skill 或知识库，会引入错误知识污染。
4. 如果电商对接先做平台特化，可能把微语主架构带偏，削弱通用性。

### 7.3 风险控制建议

1. 第一阶段只允许模板化配置，不允许自动上线变更。
2. 第二阶段所有知识/Skill 草稿必须人工审核。
3. 第三阶段只开放只读 Tool 自动执行，高风险动作默认审批。
4. 第四阶段对话式分析必须使用受控指标映射，不直接暴露任意 SQL。
